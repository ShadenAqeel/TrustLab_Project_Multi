# TrustLab Multiplayer — Human vs Human

This build extends the existing TrustLab MVP without replacing its ML models or historical experiment notebooks. A human-versus-human match runs in one browser tab per participant.

## Visitor experience

1. Open `/multiplayer`, enter a **nickname**, and press **Find a Random Opponent**.
2. The first visitor waits in a matchmaking queue. The second visitor with compatible settings is paired automatically.
3. Both humans face each other for **12 or 25 rounds**, selecting Cooperate or Defect in secret.
4. The server locks each choice. Neither browser receives the current opponent move until **both** have selected.
5. Each player sees scores, historical moves, and (in Challenge mode) whether that **player's own** precommitted model prediction was correct.
6. After the last round each player gets an **individual** K-Means behavioral profile and prediction accuracy. The pair stays human-versus-human throughout.
7. Original solo simulation is still available at `/setup`.

**Matchmaking settings:** `12 rounds + Challenge` is the default. Two visitors must select the same round count and reveal mode to enter the same queue. Names do not need to be unique; random access tokens distinguish players.

## Implementation details

- `backend/multiplayer.py` — session-scoped secret tokens, random queueing, pair-wise locking, payoff resolution, perspective-specific history, independent inference, final reports, departure handling.
- `backend/app.py` — authenticated multiplayer endpoints.
- `frontend/src/app.jsx` — join lobby, multiplayer arena, and reuse of the behavioral report.
- `web/app.js` — compiled bundle generated by `node scripts/build_frontend.js`.
- `tests/test_multiplayer.py` — match and privacy checks.

### HTTP endpoints

`POST /api/multiplayer/join` accepts `{"name":"Sam","rounds":12,"feedback":"challenge"}`. Returns a per-player secret `token` and a state snapshot.

For all other endpoints below, pass `Authorization: Bearer <token>`:

- `GET /api/multiplayer/state` — your match, readiness, and **completed** round history (polling every ~1.1 seconds).
- `POST /api/multiplayer/move` with `{"move":"C","round":1}` — locks exactly one choice for the current round.
- `GET /api/multiplayer/results` — final strategy and prediction statistics after both players complete all rounds.
- `POST /api/multiplayer/leave` — leave the queue or abandon a match.

Players' round histories are **always from their own perspective**. The current opponent move and predictions are never returned before the pair's round resolves. This avoids information leakage that would contaminate the next-move model evaluation.

### Running locally (Windows PowerShell)

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-web.txt
.\.venv\Scripts\python.exe -m uvicorn backend.app:app --host 0.0.0.0 --port 8000
```

Visit `http://localhost:8000/multiplayer`. To simulate two players on one computer, open the page in **two distinct browser windows/contexts** (e.g. normal and private browsing) and join using different nicknames. For classroom play, both visitors must reach the **same deployed server** over the Internet or local network.

### Running tests

```bash
python -m pytest tests/test_multiplayer.py tests/test_trustlab.py -q
node scripts/build_frontend.js
```

Validated in the development environment: **21 tests passed**; a complete 12-round pair was executed via the HTTP API against the actual serialized models. A second 12-round match was completed with **two isolated Chromium browser contexts** executing the compiled frontend and a bridge forwarding fetch calls to the real local API (direct browser-to-loopback navigation was restricted in the test environment). Both players reached their own final reports without browser JavaScript errors. This does not replace post-deployment browser checks over a public URL.

## Important deployment limitations

The current matchmaking service uses **in-memory state and HTTP polling**, optimized for a classroom-scale prototype on a **single** continuously running process. It has these limits:

- Restarting, redeploying, or sleeping the server loses all waiting queues and active matches.
- Do not run multiple Uvicorn/Gunicorn workers or more than one replica: they cannot share sessions. `Dockerfile` uses one worker.
- In-memory capacity is limited to 250 rooms (up to 500 concurrent players) **by software**, not a guarantee of real server capacity. Load-test with your expected number of participants first. Polling every 1.1 seconds can be expensive for large groups.
- The queue, games and nicknames expire after 4 hours. No player accounts or shared research dataset uploads are implemented.
- An opponent who disconnects may be able to return to the same match by reopening/reloading their tab. If their session remains inactive for 5 minutes, the remaining player will see an interrupted match and can join another.
- Protect public endpoints with per-IP / per-session rate limits and monitoring before running high-volume events.
- Production multiplayer should use a **durable shared store (e.g., Redis or Postgres), WebSocket events instead of polling, reconnection policy, and explicit consent before retaining participants' data**.
- The ZIP's `render.yaml` uses a free single Render web service. Free services can sleep when idle; that is undesirable during a live event. Consider an always-on service and validate compatibility before inviting a group.
- The joblib artifacts were saved in scikit-learn 1.6.1; `requirements-web.txt` pins it. Model responses are the same offline-trained models, not online training on new visitors.
- Behavioral labels from 12 or 25 rounds are **preliminary** relative to the historical 100-round research participants. The web game is a new experience, not identical to the original controlled experiment.

## Scientific scope

In this version, the human opponent remains the **same partner for the entire match** (fixed-partner condition). Shuffled-human-partner experimental sessions would require a multi-player tournament/match pool and a different data protocol. The original shuffled-partner *simulated* scenario remains in the single-player experience. Do not treat new multiplayer visitor sessions as if they were the original 188 research participants.
